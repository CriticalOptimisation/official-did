KeyRevocationRecords

A key revocation record tells a verifier three things about a signing key that its issuer has revoked: what the original public key was, from when it must no longer be trusted, and which credentials it is proven to have signed before that time. It lets anyone tell, among credentials that fail to verify because their key was revoked, the good ones from the suspect ones, without asking the issuer.

This page is the definition of the DID service type KeyRevocationRecords and of the record format. The issuer's DID document maps the term to this page in its @context.

Why revoked keys are not simply removed

When a signing key is compromised, whoever holds it can sign anything, and can write any creation date into what they sign. A credential's own date proves nothing. So every credential signed by a compromised key must stop verifying, the genuine ones too, until each is shown good by evidence the thief cannot produce, and re-issued under a new key.

Removing the key from the DID document would achieve the first part, but would also make a genuine credential indistinguishable from one signed by a random key, and would destroy the evidence needed for the second. Instead, the issuer:

  1. keeps the key's entry in the DID document, marks it revoked, and replaces its public key by a placeholder nobody can sign for, so that every verifier rejects it, including verifiers that ignore revoked;
  2. publishes the original key, and the evidence, in a revocation record, which generic verifiers never read and which cannot be used to accept a forgery.

The revoked entry in the DID document

{
  "id": "did:web:<domain>#<thumbprint>",
  "type": "JsonWebKey",
  "controller": "did:web:<domain>",
  "publicKeyJwk": { "kty": "EC", "crv": "P-256", "x": "<placeholder>", "y": "<placeholder>" },
  "revoked": "2026-10-09T12:00:00Z"
}
  • revoked is the property of W3C Controlled Identifiers v1.0: the time from which the key MUST NOT be used. Verifiers that implement it reject any proof made with the key.
  • <thumbprint> is the RFC 7638 thumbprint of the original key. It stays in the identifier: it commits to that key.
  • Every entry of the document that carried the key, under its thumbprint and under any logical name such as #key-1, is revoked the same way, at the same time.

The placeholder key

The placeholder is a valid P-256 point whose private key nobody knows, derived deterministically from the original thumbprint by RFC 9380 hash-to-curve:

suiteP256_XMD:SHA-256_SSWU_RO_
DSTDID-WEB-REVOKED-V1_P256_XMD:SHA-256_SSWU_RO_
msgthe thumbprint, as ASCII
x, ythe point's coordinates, 32 bytes big-endian, base64url without padding

Because the point is valid, every library imports it, and every signature check against it fails. Because it is deterministic, anyone can recompute it: an entry carrying any other key under a revoked identifier is not a revocation.

Finding the records

The DID document announces where its records are:

"service": [{
  "id": "did:web:<domain>#revocations",
  "type": "KeyRevocationRecords",
  "serviceEndpoint": "https://<domain>/revocations/"
}]

The record of the key with thumbprint T is at <serviceEndpoint>T.json. Its timestamp proofs are next to it, under <serviceEndpoint>T/. The endpoint may move. When it does, every record of the old endpoint must be at the new one, under the rules below.

The revocation record

{
  "id": "did:web:<domain>#<thumbprint>",
  "publicKeyJwk": { "kty": "EC", "crv": "P-256", "x": "<original>", "y": "<original>" },
  "revoked": "2026-10-09T12:00:00Z",
  "compromisedAfter": "2026-10-09T03:00:00Z",
  "log": "<URL of the issuance log>",
  "anchors": [
    { "treeSize": 18342, "rootHash": "<base64url SHA-256>",
      "ots": "<thumbprint>/18342.ots", "tsr": "<thumbprint>/18342.tsr" }
  ]
}
FieldMeaning and rules
idthe revoked identifier. Its fragment is the thumbprint of publicKeyJwk and the file name.
publicKeyJwkthe original public key. Self-certifying: its thumbprint must equal the fragment, so no other key can be substituted. Never changes.
revokedthe same value as in the DID document. Never changes.
compromisedAfterthe last moment the key is known to have been safe; at or before revoked. It may move earlier when a compromise is found to be older, never later.
logthe issuance log, an append-only Merkle log in which the issuer records every credential it signs. The log's own documentation specifies its proofs.
anchorsroots of the log, each timestamped independently of the issuer. ots: an OpenTimestamps proof whose digest is rootHash. tsr (optional): an RFC 3161 token over rootHash. Anchors are only ever added. An .ots file may be upgraded once Bitcoin confirms it, never changed to another digest.

A record holds at least the last anchor timestamped at or before compromisedAfter, and the anchor taken at revocation.

Checking a credential signed by a revoked key

A credential is suspect when the verification method it names is an entry of the DID document marked revoked, its signature fails against that entry's placeholder key, and a revocation record exists for that thumbprint. A suspect credential is:

good
when both hold:
  1. its signature verifies against the record's publicKeyJwk, the original key; and
  2. the log proves its inclusion in a root listed in anchors whose timestamp, from the OpenTimestamps proof or the RFC 3161 token, is at or before compromisedAfter.
It existed before the compromise. The log is append-only, so inclusion in one such root is enough.
unproven
otherwise. It may be genuine, issued in the last interval before the compromise, but nothing public shows it. Only the issuer's own records can say.

The issuer re-issues every good credential under a current key. A holder of a good credential can rely on it meanwhile, by this procedure. A credential that names a revoked key and is neither good nor re-issued must not be trusted.

What the issuer guarantees

  • No entry of the DID document is ever removed. An entry changes once, when it is revoked, and only as described here.
  • A record's key and revoked never change; compromisedAfter only moves earlier; anchors are only added.
  • These rules are checked before every deployment, against the document that is live at that moment, and by a monitor outside the deployment pipeline.
